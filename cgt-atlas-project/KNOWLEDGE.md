# The CGT Atlas — book project master copy

**What this is.** A book project: *The Combinatorics & Graph Theory Atlas* — a self-contained combinatorics/graph-theory book written lecture-course style ("Feynman edition": intuition and story before formalism, complete proofs, graded exercises with machine-verified worked answers, verified computational labs, and an HTML "web edition" as the standard delivery format for every chapter). Built over 57 working sessions by deep Mity (org deepsudden). The master plan, session log, to-do lists, and editorial conventions all live in the atlas file listed below.

**Why these files are here.** Canvases do **not** persist into a new chat — each new chat starts with an empty canvas area. This Knowledge topic is the durable master copy of every project file. A new chat must restore the canvases from here before doing any project work.

## Resume protocol (for a new chat)

1. **Read this file first.**
2. **Restore the canvases.** For each `cgt-*.md` file in this folder, create the folder `/home/user/canvases/<name>/` and copy the file in as `CANVAS.md` (byte-identical, e.g. by `cp`; verify with `diff`). Example: `cgt-ch2-graphs.md` → `/home/user/canvases/cgt-ch2-graphs/CANVAS.md`. There are 52 files (35 cgt-*.md masters/web editions + 16 plain .html web exports + KNOWLEDGE.md), ~6.4 MB total. The .html exports (cgt-ch1-web.html through cgt-ch16-web.html) are fully pre-rendered plain-HTML pages — the chapter content baked in as real HTML, no script, no encoded payload, readable in any browser even with JavaScript disabled — no canvas restore needed for them. Do not edit the copies in this folder during the session — treat the restored canvases as the working set. (The Ch. 1 figures companion was retired at user direction, session 33: master copy removed here, live canvas tombstoned — the platform does not support canvas deletion; its figures live byte-identically in-text in Ch. 1.)
3. **Open the atlas canvas** — "The Combinatorics & Graph Theory Atlas — Master Plan & Progress Report" (`cgt-atlas.md`) — and read its §3 session log (all rows, latest first in the table's lower half) and §5 conventions.
4. **Follow the working protocol written there:** open the atlas first; add the next session-log row marked IN PROGRESS *before* any authoring; do **one unit per session**; update the atlas after every unit; verify every claim by machine before acting; a chapter edit ⇒ rebuild and re-verify its web edition; at close, replace the IN PROGRESS row with the full record. **For long multi-step sessions (adopted session 27, user direction): track step-by-step progress in a temp Knowledge topic buffer (e.g. `cgt-<session>-buffer`) — files in /home/user do NOT survive restarts; update the buffer after every completed step and sync each edited canvas over its master here; delete the buffer topic at close.**
5. **Before the chat ends, refresh this folder** (see the stale-copy rule below).

## Standing goal — canon coverage (self-sufficiency instruction)

The project's ultimate goal is **full coverage of the load-bearing canon**: every important solved problem family of combinatorics & graph theory, and every repeatable solution pattern, properly arranged into chapters (the atlas's Purpose section states this; its own honest caveat is that the *canon*, not "all problems ever published", is the target). The chapter map and the P-index are the **coverage ledger** — the ledger grows (P21–P23, Dirac, the Volume II outline all arrived this way), but nothing executes the ledger against the *field* unless instructed. Therefore:

- **Every few sessions — and always before starting a new chapter or Volume II unit — run a canon coverage audit:** compare the chapter map + pattern index + all backlogs against the field's standard references (the atlas's sources-of-truth list: van Lint & Wilson; Diestel; Alon & Spencer; Bollobás; Lovász; Stanley; West; Engel) and any needed searches; name what is load-bearing but absent (problem families, patterns, whole areas); propose where each belongs (new chapter, new problem family in an existing chapter, new pattern ID) — and record the audit in the session log. The audit *proposes*; the user approves scope before execution, as always.
- **On the next atlas edit, add this as a standing to-do item in the atlas itself** (it currently lives only here) so the instruction survives even this folder being reorganized.
